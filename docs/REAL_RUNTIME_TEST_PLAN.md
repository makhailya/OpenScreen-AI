# Ограниченный план реальной проверки

Это план будущей сессии, для которой потребуется отдельное явное разрешение.
При подготовке и проверке этого документа не запускались GUI, Ollama-запросы,
модели, микрофон, запрос TCC или реальный тест производительности. Адрес службы, установленная
модель и разрешение macOS на микрофон сейчас **не проверены и недоступны этой
проверке**. Не объявляйте их работающими или неработающими до разрешённого
ручного запуска.

## DAY-001 gate и решения владельца

Этот документ остаётся планом. Во время DAY-001 не запускались GUI, Ollama API,
модели, микрофон, системное аудио, TCC-проверки или реальные benchmark. По
результатам INT-002B.1 отсутствовали STT dependencies и configured model paths,
а pytest 8 отсутствовал в Python 3.12 окружении. Поэтому первый live run —
**NO-GO**, пока владелец отдельно не утвердит все пункты ниже и не подготовит
локальную среду по [ENVIRONMENT_SETUP.md](ENVIRONMENT_SETUP.md).

До сессии владелец должен принять решения:

1. Какое Python окружение использовать: поддерживаемую связку Python 3.12 и
   pytest 8 для тестов; проверить уже установленный Python и ARM64 без установки.
2. Какие версии/источники Parakeet и Silero VAD использовать и где хранить
   четыре файла Parakeet и отдельный VAD asset.
3. Какой фактически доступный локальный Ollama tag выбрать вместо невыверенного
   сочетания `AppConfig` default и `.env.example`.
4. Разрешить ли открыть выбранный микрофон и показать macOS TCC prompt.
5. Разрешить ли один ограниченный реальный STT → LLM → UI inference после
   успешного preflight.

Не запускайте следующий этап без явного решения по каждому пункту. Наличие
локального manifest, успешного doctor или fake suite не заменяет этих решений.

### Preflight перед разрешённой live сессией

- [ ] Записать Git SHA и подтвердить чистое дерево тестового worktree.
- [ ] Проверить `python --version`, `python -m pytest --version`, package
  metadata для `numpy`, `sherpa-onnx`, `sounddevice`, PySide6, httpx и dotenv.
- [ ] Запустить `python -m openscreen_ai doctor`; хранить только категории и
  PASS/WARN/FAIL, не выводить env values или локальные пути.
- [ ] Проверить локально наличие и чтение Parakeet/VAD файлов; не загружать
  модель ради doctor.
- [ ] Подтвердить выбранный Ollama tag и loopback конфигурацию в приватном
  терминале, не записывая чувствительные значения в отчёт.
- [ ] Убедиться в наличии свободной RAM/диска по правилам владельца и определить
  способ мониторинга RSS/CPU до запуска.
- [ ] Получить отдельное разрешение на GUI, TCC, микрофон и первый inference.
- [ ] Назначить тестовые фразы и критерии распознавания до запуска; использовать
  только согласованные фразы и не сохранять сырое аудио.

### Сценарии и измерения

В рамках одной короткой сессии запускать последовательно, фиксируя реальный
результат, а не предполагаемый:

| Сценарий | PASS/FAIL evidence |
|---|---|
| Короткая заранее согласованная фраза | Текст получен один раз, соответствует принятому владельцем критерию; очередь и worker завершены |
| Длинная фраза | Не потерян/не продублирован результат; заметки о сегментации и endpoint |
| Паузы внутри речи и длинная пауза в конце | UI остаётся отзывчивым; endpoint соответствует согласованному поведению |
| Контролируемый фоновый шум | Ошибки и качество отмечены; не делать общий вывод о качестве по одной фразе |
| Повторные запросы | Каждый одобренный transcript порождает один ответ; после завершения можно начать следующий запрос |
| Отмена во время STT | UI остаётся отзывчивым, input/worker освобождены, поздний transcript не запускает LLM |
| Отмена во время LLM | HTTP response закрыт, поздние chunks отброшены, можно повторить после завершения worker |
| Закрытие окна при активных STT/LLM | Окно закрывается только после завершения worker; нет зависшего процесса или QThread |
| Недоступный Ollama / несовпавший model tag | Фиксированная безопасная ошибка без prompt/error body; UI восстанавливается после завершения |
| Восстановление после ошибки | Новый разрешённый цикл стартует один раз; логи не содержат transcript, prompt или traceback с данными |

До и после каждого запуска записывайте время STT initialization, monotonic
endpoint→decode latency, LLM TTFT, end-to-end latency, peak RSS, CPU, количество
ошибок, queue max depth, dropped blocks, VAD resets, stop duration и итоговое
состояние worker. Секреты, transcript, prompt, аудио и абсолютные приватные пути
в общий артефакт не добавлять.

Числовые latency/RSS пороги пока не подтверждены измерениями MacBook Air M4.
Предварительные гипотезы для согласования владельцем: GUI event loop не должен
блокироваться дольше одного обычного кадра интерфейса при start/cancel/close;
baseline очередь должна иметь `dropped_blocks == 0`; все bounded worker должны
закрыться в заранее выбранный оператором срок. Это не принятые критерии и их
нужно заменить числовыми лимитами до реального теста. Порог качества речи
следует определить отдельно на согласованном наборе фраз.

### Условия немедленной остановки

Остановите сценарий при несанкционированном аудио/сетевом доступе, выводе canary,
transcript, prompt, credential или приватного пути, зависании UI, потере/дубле
обязательного результата, невозможности закрыть worker, неожиданном выборе
устройства или отказе TCC. Отметьте тест как FAILED или BLOCKED; не повторяйте
его и не меняйте настройки системы автоматически.

Цель — собрать контролируемые функциональные данные и измерить задержки,
очередь и память, не превращая предварительную проверку или синтетические
тесты в заявление о готовности к production. Числовые пороги задержки и памяти
здесь намеренно не придумываются. До решения о выпуске владелец продукта
должен определить приемлемые пороги и критерии качества речи для целевого
устройства и модели.

## Разрешения и подготовительные условия

1. Получите отдельное явное разрешение до запуска GUI, обращения к локальной
   Ollama, создания реальной STT-модели, воспроизведения аудио или открытия
   микрофона. Флаг CLI --allow-real-model — дополнительный программный
   предохранитель, а не пользовательское разрешение.
2. Запустите python -m openscreen_ai doctor из корня проекта. Остановитесь,
   если не пройдена базовая проверка или проверка конфигурации. WARN stt
   означает, что необязательный речевой режим не готов; настройте его приватно
   до этапа STT.
3. Приватно проверьте настройки LLM и сверьте ожидаемое имя модели с локальным
   выводом ollama list (эту команду упоминает README). Doctor не соединяется с
   Ollama и не проверяет наличие модели. Не публикуйте адрес службы, имя модели,
   учётные данные или пути.
4. Проверьте четыре файла Parakeet и отдельный файл Silero VAD из
   [RUNTIME_READINESS.md](RUNTIME_READINESS.md). Подтвердите наличие
   необязательных зависимостей и Python 3.12–3.13. Не скачивайте модели во
   время тестовой сессии.
5. Используйте только одобренное оператором неперсональное аудио. Храните
   аудиофайлы и manifest реального режима в закрытом локальном каталоге.
   Адаптер чтения аудиофайлов принимает WAV PCM16LE mono 16 kHz или raw s16le
   mono 16 kHz с явно заданным количеством сэмплов; другие частоты и число
   каналов он отклоняет, а не пересэмплирует.
6. Для проверки интерфейса/микрофона оператор должен отдельно одобрить тест
   аудиоустройства до запуска. Вручную проверьте macOS System Settings →
   Privacy & Security → Microphone. Не автоматизируйте системный TCC-запрос и
   не меняйте разрешения. Если доступ запрещён, выбрано неожиданное устройство
   или разрешение отсутствует, пропустите этап и отметьте его BLOCKED.

Оставьте .env без изменений. Если тесту требуются временные настройки,
передавайте их только окружению тестового процесса. Для каждого измерительного
запуска выбирайте новый пустой путь результата: инструмент отказывается
перезаписывать существующие JSON/CSV. В артефакт записываются хеши и метрики,
но не расшифровка, аудиоданные, пути моделей, имена аудиоустройств или пути
входных файлов. Перед публикацией всё равно проверьте артефакт локально.

## Временные рамки и сценарии

Ограничьте одну одобренную сессию **45 минутами**:

| Этап | Максимум |
|---|---:|
| Предварительная проверка, локальная подготовка и приватная проверка manifest | 5 минут |
| GUI, текстовый запрос и одобренные сценарии микрофона/TCC | 5 минут |
| Три STT-запуска по аудиофайлам | 27 минут 45 секунд дедлайнов дочерних процессов и ещё до 6 секунд на ограниченное завершение (27 минут 51 секунда всего) |
| Проверка результатов, очистка и заметки | 5 минут |

Три измерительных запуска используют одни и те же шесть развернутых фраз,
одну модель, VAD, конфигурацию и компьютер; суммарная длительность аудио в
manifest не превышает 45 секунд. Для каждого запуска задано ожидание результата
5 секунд. Исходный код вычисляет дедлайн дочернего процесса как плановая
длительность аудио + 30 секунд резерва на запуск и 5 секунд ожидания результата
на каждый аудиофрагмент + 300 секунд резерва на вычисление fingerprint. Для
шести фрагментов и лимита воспроизведения 45 секунд это не более 555 секунд (9 минут
15 секунд) на запуск, затем не более 2 секунд на ограниченное завершение. Для
трёх запусков получается 27 минут 45 секунд дедлайнов и до 6 секунд резерва
на завершение. Завершите сессию через 45 минут, даже если подготовка или
очистка заняли больше времени; не увеличивайте лимит и не повторяйте timeout
в этой сессии.

Предлагаемый порядок измерительных сценариев:

1. **Базовый запуск A:** реальная модель на аудиофайлах, ёмкость очереди 20
   (значение адаптера по умолчанию).
2. **Ограниченная очередь:** те же шесть развернутых фраз и настройки, ёмкость
   очереди 2. Это сравнение очереди адаптера, а не очереди живого микрофона и
   не целевой порог производительности.
3. **Базовый запуск B:** повтор с ёмкостью очереди 20, чтобы заметить изменение
   условий вокруг запуска с ограниченной очередью.

Создайте приватный manifest с тремя заранее проверенными аудиофрагментами:
коротким, средним и длинным. Для каждого задайте repeat: 2, итого получится
шесть развернутых фраз; суммарное воспроизведение не должно превышать 45
секунд. До запуска зафиксируйте частоту дискретизации и целочисленные границы
truth_start_sample / truth_end_sample. Не меняйте manifest, аудио, модель, VAD,
число потоков или провайдер между базовыми запусками и сценарием ограниченной
очереди. Для каждого вызова выбирайте новое имя JSON-файла; рядом инструмент
создаст CSV-файл. Код отклоняет manifest больше исходных лимитов: 100 развернутых
фраз, 16 МиБ manifest, 2 ГиБ суммарного аудио, и не перезаписывает результаты.

Проверенные в tools/stt_benchmark.py параметры реального режима: --mode real-model,
--manifest, --output, --model-dir, --vad-model-path, --max-replay-seconds,
--queue-capacity, --result-timeout-seconds и --allow-real-model. Для отдельно
разрешённой сессии каждый запуск использует одинаковые параметры; меняются
только имя результата и ёмкость очереди:

```sh
python tools/stt_benchmark.py --mode real-model \
  --manifest '<private-manifest.json>' \
  --output '<new-run-name.json>' \
  --model-dir '<local-parakeet-directory>' \
  --vad-model-path '<local-silero-file>' \
  --max-replay-seconds 45 \
  --queue-capacity 20 \
  --result-timeout-seconds 5 \
  --allow-real-model I_AUTHORIZE_REAL_MODEL_EXECUTION
```

Аргументы в угловых скобках — заполнители: замените их приватными локальными
путями и новым именем результата, не копируйте скобки буквально. Точная строка
подтверждения проверяется исходным кодом, но сама по себе не даёт разрешения
на выполнение. Эта команда не запускалась при выполнении текущей задачи.

Для отдельного этапа интерфейса/микрофона используйте документированную команду
python -m openscreen_ai.main только после разрешения. Возьмите небольшой
фиксированный набор неперсональных фраз: короткую, среднюю и длинную; повторите
каждую три раза, если укладываетесь в лимит этапа 5 минут. Сначала проверьте
текстовый запрос и общее сообщение об ошибке, затем запуск STT, остановку,
повторный запуск и закрытие окна. Этот этап проверяет интерфейс, Ollama и TCC,
но не даёт привязанной к аудио разметки сэмплов для измерения задержек выше.

## Часы и измерения

Не смешивайте три шкалы времени:

1. **Шкала аудио/сэмплов:** каждая граница речи задаётся целочисленным индексом
   сэмпла. Переводите его во время аудио только как sample_index / sample_rate;
   при 16 kHz 16 000 сэмплов составляют одну секунду. При воспроизведении из
   файла адаптер сопоставляет эту точку монотонной шкале по формуле
   replay_origin_perf + sample_index / sample_rate.
2. **Монотонные часы выполнения:** отметки времени worker, endpoint, decode,
   controller и фиксация результата в тестовом инструменте используют time.perf_counter() от начала
   replay. Не вычитайте число сэмплов из значений perf_counter().
3. **Шкала наблюдения результата:** result_observed_at — момент, когда
   тестовый инструмент получил сигнал результата. Это отдельное событие, не
   совпадающее с завершением сегмента аудио, окончанием decoder, отправкой сигнала worker,
   получением его controller или показом текста в интерфейсе.

Для каждой фразы сохраните sample rate и truth boundaries, а также раздельно
фиксируйте метрики vad_endpoint_audio_lag_ms, vad_endpoint_wall_ms,
decode_after_endpoint_ms, result_latency_ms, recognition_ms,
worker_to_controller_ms и controller_to_callback_ms. В отчёте укажите число
измерений и распределение задержек; используйте квантили nearest-rank,
описанные инструментом. Значение null означает отсутствие данных: не
подставляйте вместо него ноль и не смешивайте задержку endpoint со временем
декодирования.

Для оценки ресурсов отдельно фиксируйте model_startup_ms (задержку запуска
модели), CPU процесса, CPU декодера и метрики rss_current_bytes / rss_peak_bytes.
Код использует resource.getrusage
ru_maxrss: максимум памяти процесса мог быть достигнут до этого запуска,
а current RSS может иметь значение null. Указывайте эти ограничения рядом с
любым сравнением памяти; не выдавайте максимум процесса за пик только данного
запуска. Сохраняйте состояние doctor и порядок запусков рядом с артефактами.
Сравнивайте только одинаковые аудиометки, model/VAD hashes, версию Python,
компьютер и конфигурацию. Хеши аудио, конфигурации и модели помогают
сопоставить артефакты, но не доказывают качество модели.

Для сравнения очередей записывайте queue_capacity, максимальную глубину,
dropped blocks, input overflow notifications и счётчики сброса VAD. Потери в
сценарии capacity 2 — наблюдения ограниченного воспроизведения; опишите их
влияние на результат. Потеря блока в baseline capacity 20, отсутствие
результата, неожиданный input overflow или сброс/ошибка, из-за которых сценарий
не состоялся, требуют остановить следующие запуски и разобраться. Не выдавайте
результат воспроизведения из файла за измерение производительности микрофона.

Порогов задержки, RSS, частоты ошибок слов (WER) или CPU в этом плане нет. До решения о
выпуске согласуйте с владельцем продукта пороги целевого устройства и рубрику
оценки расшифровки. Пока они не определены, публикуйте исходные измерения, а
оценку производительности/качества отмечайте как **не оценено (unrated)**.

## Функциональные PASS/FAIL и условия остановки

Запуск на аудиофайлах получает **PASS**, только если заранее заданные шаги
завершились в пределах временного лимита, получены все шесть ожидаемых строк
аудиофрагментов и сигналов результатов, дочерний процесс завершился штатно,
а артефакт прошёл проверку приватности. Для сценария с интерфейсом требуются
одобренные текстовый/STT-потоки, безопасные общие сообщения об ошибках,
состояние окна ожидания/закрыто и отсутствие активного worker после остановки
или закрытия. Качество расшифровки оценивайте только по согласованной до
запуска рубрике; иначе оно не оценено.

Отмечайте **FAIL**, если произошла неожиданная ошибка инициализации/decoder,
потерян или продублирован обязательный результат, базовая очередь теряет
блоки, не сработали остановка/закрытие, остался worker/дочерний процесс, артефакт
некорректен или превышен лимит времени. В сценарии с ограниченной очередью
могут наблюдаться drops; зафиксируйте их и влияние на результат. Они сами по
себе не означают сбой тестового инструмента, но функциональный сценарий не
проходит, если потерян ожидаемый результат. Отказ в разрешении, отсутствие
службы/модели или одобрения оператора — это **BLOCKED**, а не PASS и не
свидетельство готовности к production.

Немедленно прекратите проверку, если:

- Оператор отозвал разрешение, macOS отказала в доступе или выбрано другое
  устройство, чем то, которое было одобрено.
- Аудио, расшифровка, prompt, учётные данные, приватный путь или данные модели
  попали в общий лог/артефакт либо заранее заданная контрольная строка privacy
  canary появилась в интерфейсе или логе.
- URL не loopback, служба/модель не совпадает с приватно подтверждённой целью
  или процесс неожиданно обращается к внешней сети.
- Не прошёл базовый аудиофрагмент, появились потери при queue capacity 20,
  интерфейс перестал отвечать, worker не остановился или превышен любой
  жёсткий лимит времени.

После остановки не начинайте следующий сценарий и не повторяйте запуск.
Отметьте результат как failed или blocked, сохраните только безопасные данные
для диагностики, остановите приложение и дождитесь завершения controller.
Тестовый инструмент реального режима ограничивает время дочернего процесса,
затем выполняет terminate/kill/join; если дочерний процесс завершился с
ошибкой или timeout, файл результата не записывается. Перед завершением
сессии убедитесь, что процесс и worker приложения действительно завершились.
